4.1、从三原语到四原语的API形态

截止目前为止10-21，官方文档仅对三种原语有明确的契约定义，但 jev‑1.14 发布的博文当中公布了一个实验性质的第四种独立原语，专门做图像目标框检测（bounding box）：

  • Box：图像定位，在输入图像里找出描述目标的包围框

    • TypeSafe 内部描述它是 “处于决策灰色地带的新类型”：它不是分类打分，但同样是类型化、固定 schema 的结构化输出，延续 System One“不生成自由文本、输出强类型”的整体范式；

    • 输入侧的state里会携带图像（PNG/JPEG，单文件上限 16MiB，单请求图像总上限 32MiB，边长范围 256–1568px），然后在 questions 里定义一条 type: "box" 的问题，附带文本指令 instructions，描述你要找什么目标；

      ```HTML
{
  "model": "jev-1.14.0",
  "state": "<base64图像>",
  "questions": {
    "obj1": {
      "type": "box",
      "instructions": "图中的猫"
    }
  }
}
```

  • 约束：一个 box 问题只能输出单个框；如果图里有多个同类目标，不能一次返回多个 bbox，需要多 question 或者业务层循环。

    • 返回的 box 字段是归一化坐标（相对图像宽高，值域 [0,1]，左上角原点）:

      ```JSON
{
  "obj1": {
    "box": {
      "left": 0.12,
      "right": 0.55,
      "top": 0.20,
      "bottom": 0.81
    },
    "confidence": 0.87
  }
}
```

  • 这实际之前讨论的“Jev仅处理文本模态”相对应，官方最新修正了对外说法来回应对多模态的支撑问题：多模态/长上下文能力一直存在、只是此前未在公开文档显式承诺！

其余三种原语这里不再多做解释，开源方案也多遵循相应的原语设计，其核心根源在于：三原语覆盖的决策空间恰好对应了 “选、评、判” 三类原子动作：选（K 个互斥选项里挑一个，Choice）、评（在有序量表上定位，Score）、判（单一命题是否成立，Noul）—— 任何更复杂的决策（多标签、多目标、层级路由）都被可以被设计为 “把复杂问题拆成多个三原语问题、在一次请求里调用”，而不是新增第四种原语。

官方文档：https://docs.typesafe.ai/primitives

原语 语义 返回字段 硬约束
Choice 从 K 个枚举选项中选一个；K 较大时先对各选项独立打分、再做显式选择（两阶段） choice / probabilities（和为 1）/ confidence 每 Choice 最多 255 个选项；api.md："You can have a maximum of 255 options per Choice"
Score 在有序 rubric 层级上打分，score 为概率加权期望位置（可落在两层之间） score / legend / probabilities / confidence 至少 2 级、最多 10 级；api.md："A Score should have at least two levels; the API accepts up to 10"
Noul 单一命题 yes/no，返回 yes 的概率 noul（0=no、1=yes 的概率） 二值；命名一说源自 Bernoulli 分布【转引，第三方插件 README；官方文档未见词源说明】

如下为一个调用和响应示例，仅做说明：

# 请求调用，一次多个
POST /v1/systemone
{
  "model": "jev-latest",
  "state": "<工单/日志/待判断文本>",
  "questions": {
    "q1": { "type": "noul",   "body": "此工单是否需人工处置？" },
    "q2": { "type": "choice", "body": "归入哪类？", "options": ["骚扰","垃圾","自伤","其他"] },
    "q3": { "type": "score",  "body": "紧急度？",    "legend": [0,1,2,3,4] }
  }
}
# 响应示例
{
  "q1": { "noul": 0.72 },
  "q2": { "choice": "垃圾", "probabilities": {"骚扰":0.10,"垃圾":0.72,"自伤":0.03,"其他":0.15}, "confidence": 0.72 },
  "q3": { "score": 1.43, "probabilities": {0:0,1:0.57,2:0.43,3:0,4:0}, "confidence": 0.35 }
}

4.2、可外部验证的计算语义

语义 官方原文 / 数值 对调用方的含义
并行独立评估 "Every question is evaluated independently, so adding more questions does not create context-rot" 同一 state 上独立承载多少问题，问题之间互不污染；这是对生成式模型“多问共上下文导致提示干扰”的结构性回答
扇出延迟近常数 fan-out.md："sending many questions in a single API call… adding more questions usually has little effect on response time" 多问题摊销的是同一次 state 处理成本；官方未给单请求问题数硬上限【问题数量不上限】
上下文窗口 64k tokens / 请求；
其中 state + 最长问题 ≤ 32k；		 长 state（工单、日志全文）占用的是 32k 子预算
限流 100K tokens/second + 80 requests/second（动态调整中，超限返 429） 官方标注“动态调整中”，非 SLA 承诺
输入计费规则 按 input token 计费，output token 免费
 响应是结构化字段而非逐 token 生成，输出没有边际成本

除了上述偏向服务验证的部分，我们还需要关注的是两个可外部复核的语义点：

  • Choice 的 probabilities 与为 1、Score 的 score = \(\sum{level × p(level)}\) 都是纯算术，调用方可本地复算；

    • 比如：3 级量表 {0,1,2} 上 p=(0, 0.57, 0.43) → score=1.43（算术为本报告按官方定义复算）；

    • 这是官方输出契约里少数不依赖厂商说法即可验证的部分【[https://docs.typesafe.ai/primitives/choice.md](https://docs.typesafe.ai/primitives/choice.md)】。

  • 高基数 Choice 走两阶段：

    • 官方博客原文 "Jev supports a cardinality up to 255. For the higher cardinality choices, we do a 2 stage-system of scoring independently then making an explicit choice"【官方，[https://typesafe.ai/blog](https://typesafe.ai/blog)】

    • 这解释了为什么 255 不是“模型一次能看见多少选项”的语义上限，而是“显式选择阶段”的工程上限；

另外，一些关于成本/上下文预算的限制与推测也需要关注：

  • 64k 是模型单次请求的总上下文，其中 state + 最长问题不得超过 32k【[https://docs.typesafe.ai/models.md](https://docs.typesafe.ai/models.md)】

    • 这意味着长工单/长日志可以整段塞进 state，但任何单个 question 的文本长度仍受 32k 子预算约束；

    • 多问题同时决策时，各问题共享 32k 中的 state 部分，问题本身逐条计费进 input token；

    调用方做长 state 集成时，应把 state 长度与最长 question 放在一起核算，而不是只看 64k 总量；

  • 尚不明确：state 是否前缀 KV 复用、选项间是否 listwise 交互、读出头是 pointer 还是 slot、后向信息流是否存在；

4.3、命名来源

名字 出处 含义
System One（类名） Kahneman《Thinking, Fast and Slow》的快思考系统
- [https://typesafe.ai/blog](https://typesafe.ai/blog) FAQ		 对应“快速、直觉、低功耗”的系统；与慢速推理/生成式 System Two 相对
Jev（模型名） 纪念 William Stanley Jevons（威廉·斯坦利·杰文斯）
- [https://typesafe.ai/blog](https://typesafe.ai/blog) FAQ		 取“杰文斯悖论”之意：蒸汽机效率提升反而增加煤耗——类比决策智能的单位成本下降后，用例总量反而上升

杰文斯悖论放在本产品语境里的具体主张是：当单个决策的边际成本压到可忽略量级（$0.042/MTok、输出免费、70–500ms），调用方不会因此少做决策，反而会把决策嵌入到以前“不敢自动化”的高频链路里（每工单多个危害检查、每帧一次 GUI 判断）——总用量随单位效率上升而上升
